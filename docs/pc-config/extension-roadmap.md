## 1. 优先级与红线

- **P0**：直接影响报价可信度、兼容性正确性或候选覆盖，进入下一迭代。
- **P1**：提升可追溯性与产品体验，需要契约或数据模型变更。
- **P2**：依赖外部数据源或合规评估，先做技术验证再排期。
- **红线（不可协商）**：不得通过修改求解规则放宽预算；不得把 `MOCK_DEMO` 展示为已核验价；不得伪造核验时间、购买链接或跑分；`UNKNOWN` 不得降级为 `PASS`；任何价格必须带来源与时间。

## 2. 后续项

Stage 8 已完成离线数据治理：8,238 条硬件主数据、生命周期分类、四类发布候选池与第三方映射输入，详见 [治理报告](../quality/hardware-data-governance-report.md)。这些产物**尚未接入运行时**，因此下表 P0 的“扩展候选”只有在 Stage 9 接入真实报价后才会体现在在线推荐结果中。

| 优先级 | 后续项 | 目标 | 影响面 | 前置条件 | 验收方式 |

| P0 | 真实报价替换 18 条 `MOCK_DEMO` | 28 条器件全部有可追溯真实报价，`verifiedOnly` 可独立成单 | Java 报价仓储与 fixture；Agent 提示与投影；前端演示价横幅；数据核验台账 | 每个 `hardwareId` 至少 1 条可访问链接；记录核验时间、平台、SKU；许可证与抓取合规确认 | `verifiedOfferCount=28`、`mockOfferCount=0`；`requireVerifiedOffers=true` 时在已支持预算档内可解；无演示价横幅；端到端用例不出现 `MOCK_DEMO` |

## 3. 实施顺序

1. 先完成 P0 的数据与规则修正，并同步更新 [`candidate-shortlist.md`](./candidate-shortlist.md) 与 [`testing-and-evaluation.md`](./testing-and-evaluation.md)。
2. P1 涉及字段或接口变更时，先改根 [`docs/api-contract.md`](../api-contract.md)，再同步 Java DTO、Agent 投影、前端类型与契约快照。
3. P2 先做只读技术验证，不进入主求解链路；验证通过后再评估是否立项。

## 4. 风险与回滚

| 后续项 | 主要风险 | 缓解与回滚 |
| --- | --- | --- |
| 真实报价 | 链接失效、价格波动、来源下架 | 保留 `validUntil` 与核验时间；过期报价不参与 `verifiedOnly`；失败时返回结构化无解，不回退演示价 |
| 散热限高 | 数据缺失被误判为通过 | 缺失继续返回 `UNKNOWN`；规则版本号随行为升级；回滚仅需回退规则版本与 fixture |
| 扩展候选 | 组合数膨胀导致求解变慢 | 设置候选上限并记录 `evaluatedCombinationCount`；先压测再调参 |
| 硬件版本化 | 迁移破坏历史快照 | 迁移前备份；新旧 ID 双读；保留回滚脚本与迁移测试 |
| 多方案对比 | 响应体增大、前端渲染变慢 | 限制方案数量与字段；对比视图按需加载 |
| 快照保留 | 误删审计数据 | 先归档后清理；软删除与审计日志；保留期可配置 |
| 自动比价/抓取 | 封禁、限流、合规争议 | 遵守站点条款与 robots；限流与缓存；失败不阻塞主流程；保留人工复核 |
| 二手与整机 | 成色、保修、拆分口径混乱 | 未定义前保持【未实现】，明确拒绝并引导用户选择新机配置 |

## 5. 度量口径

- 报价可信度：`verifiedOfferCount / total` 与 `mockOfferCount`；P0 验收要求演示价为 0。
- 兼容性可判定率：非 `UNKNOWN` 检查数 / 总检查数；散热限高补齐后应覆盖全部在售机箱。
- 预算硬约束：越预算方案数必须为 0，失败时返回 `BUDGET_EXCEEDED` 与最低可行预算。
- 求解可用性：目标预算档有解率；新增档位必须同时有 fixture 与 eval 用例。
- 性能基线：记录 solve 延迟与首个 `token` 延迟；目标值在实施前用真实数据测定，不在本文臆造。
