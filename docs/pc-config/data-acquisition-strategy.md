## 0. 结论摘要

1. 硬件主数据 8,238 条，其中**明确优先采集池 3,967 条（48.2%）**，即「可售集合」。
2. 已发布运行时数据：目录 201 条、报价 201 条（10 人工核验 + 18 演示 + 173 平台观测）。
3. 覆盖率低的类别不是「没搜到」，而是**标题结构与主库型号体系不匹配**：CPU/GPU 多型号混卖、存储多容量混卖、机箱中文系列名。
4. 关联唯一键是 `hardware_id`，采集结果必须先过「主库唯一命中」校验才能生成报价。
5. 当前上线**不经过数据库**：报价是 classpath JSON，随镜像发布；入库方案见 §8.2【待实现】。

## 1. 数据分层

| 层 | 含义 | 载体 | 当前规模 |
| --- | --- | --- | ---: |
| L0 主库 | 清洗后的全量硬件，唯一事实源 | `data/pc-config/master/hardware-master.jsonl` | 8,238 |
| L1 可售池 | 有在售证据、进入采集计划的子集 | `data/pc-config/export/marketplace/sellable.json` | 3,967 |
| L2 观测 | 平台检索/详情得到的原始商品与报价候选 | `marketplace/raw/`、`listings.jsonl`、`matches.jsonl`、`detail/` | 682 商品 / 201 SKU |
| L3 报价候选 | 通过唯一命中与价格校验的报价 | `market_offers.json`、`llm_offers.json` | 173 + 待生成 |
| L4 运行时 | 服务实际加载的目录与报价 | `application-service/.../pc-config/*.json` | 201 / 201 |

规则：**上层只能从下层派生**，禁止跳过 L1 直接对 L0 全量采集，也禁止绕过 L3 直接改 L4。

## 2. 采集优先级

### 2.1 分层与计数

| 优先级 | 定义 | 条数 | 占主库 | 状态 |
| --- | --- | ---: | ---: | --- |
| T0 | 人工核验/演示价，保证整机可解 | 28 | 0.3% | 已发布 |
| T1 | 平台观测价 EXACT 命中并入库 | 173 | 2.1% | 已发布 |
| T2 | 已采集详情、待拆解的混卖链接 | 14 条链接 / 201 SKU | — | 采集中断于 LLM 凭证 |
| T3 | 可售池（明确优先采集） | 3,967 | 48.2% | 待采集 |
| T4 | 全量主数据 | 8,238 | 100% | 暂不采集 |

**「明确优先采集」= T3 = 3,967 条**。T0–T2 是 T3 中已先行的部分，不额外扩张口径。2026-11-09 起在 T3 内再收缩，见 §12。

### 2.2 优先理由（三个信号，全部满足才进 T3）

1. **品牌白名单**：国内主流在售品牌（华硕、微星、技嘉、七彩虹、影驰、金士顿、芝奇、三星、西数、致态、利民、九州风神、长城、航嘉等）。
2. **代际窗口**：CPU/GPU/主板/存储只留当前两代（如 Intel 13/14 代与 Core Ultra、AMD AM5、RTX 40/50、RX 7000/9000、DDR5、PCIe 4.0/5.0）。
3. **市场存在性**：同型号族在淘宝/京东有在售商品；无货源、已停产、仅 OEM 的型号直接排除。

按类别（主库 / 可售 / 已报价）：

| 类别 | 主库 | 可售 | 已报价 | 可售占比 |
| --- | ---: | ---: | ---: | ---: |
| CPU | 493 | 71 | 6 | 14.4% |
| GPU | 1,109 | 284 | 4 | 25.6% |
| 主板 | 781 | 512 | 65 | 65.6% |
| 内存 | 1,891 | 1,107 | 16 | 58.5% |
| 存储 | 1,485 | 214 | 6 | 14.4% |
| 散热 | 863 | 589 | 66 | 68.3% |
| 机箱 | 1,098 | 822 | 5 | 74.9% |
| 电源 | 518 | 368 | 33 | 71.0% |
| **合计** | **8,238** | **3,967** | **201** | **48.2%** |

### 2.3 同优先级内的排序

按「能否拼成一台整机」加权，而不是按条数：

1. **闭环优先**：同一插槽/平台的 CPU + 主板 + 内存 + 散热 + 机箱 + 电源组合先采。
2. **价格敏感件优先**：GPU、CPU 先于机箱、散热。
3. **同族去重**：同一芯片/型号族只采代表 SKU（见 §4.2）。

## 3. 采集通道与调度

| 通道 | 用途 | 输入 | 输出 | 约束 |
| --- | --- | --- | --- | --- |
| A 搜索卡片 | 批量发现商品与展示价 | 检索词（型号族） | `raw/*.json`、`listings.jsonl` | 每次 ≤10 条；仅 `default/sale/price` 排序 |
| B 详情 + SKU | 拆解多型号混卖 | 商品链接 | `detail/<item_id>.json` | 冷却 10 秒；单条约 15 秒 |
| C 人工核验 | 高价值/争议报价 | 京东自营或品牌旗舰店 | `offers.template.json` | 人工确认店铺、SKU、到手价 |
| D 目录发布 | 生成运行时目录与跑分 | master JSONL | `catalog.json`、`benchmarks.json` | 原子写 `os.replace` |

调度规则：

- 搜索阶段一次 80 条检索串，断点续跑；失败不消耗重试配额，但会重置冷却。
- 详情阶段逐条串行，每个商品独立落盘，失败可单条重跑。
- **任何阶段都不得把 FAMILY 级匹配写入报价**，只有 EXACT（品牌 + 型号唯一命中）才允许定价。
- 采集脚本全部从仓库根运行，产物只写 `data/pc-config/export/**`（已 gitignore）。

## 4. CPU / GPU 覆盖不足的根因与解法

### 4.1 根因

| 现象 | 真实原因 |
| --- | --- |
| CPU 2/71 有效 | 16 条商品中 12 条一链接多型号，只有一个展示价 |
| GPU 0/284 有效 | 主库是「芯片型号 + 品牌 SKU」，标题是中文品牌 + 芯片，品牌无法映射只能判 FAMILY |
| 存储 3/214 有效 | 一链接混卖容量/系列（NV3/KC3000、990 Pro 1T/2T） |
| 机箱 2/822 有效 | 主库英文型号，标题中文系列名，匹配器退化为同一条 FAMILY |

### 4.2 解法

**CPU：SKU 面板拆解（已跑通）**

- 详情页 `__ICE_APP_CONTEXT__` 内含 `skuBase.skus` 与 `skuCore.sku2info`，可直接读出「规格 → 价格」矩阵，无需逐个点击。
- 实测 14 条链接共 201 个 SKU，单条覆盖 9–20 个型号。
- 目标：71 个可售 CPU 型号全部有价；按每条覆盖 8 个型号估算，约 10–12 条链接。

**GPU：芯片级聚合**

- 284 个可售记录只对应 **30 个不同 `model_name`**（同芯片不同品牌/散热版本）。
- 采集与定价按「芯片 + 显存」聚合，品牌作为可选证据：`RTX 5070 Ti 16GB` 采一个代表 SKU 即可。
- 校验必须同时命中芯片与显存后缀（8G/12G/16G），避免 4060 命中 4060 Ti。
- 目标：30/30 芯片有价，覆盖 284 条可售记录。

**存储 / 机箱（后续）**

- 存储检索词带容量（如「金士顿 NV3 1TB」），匹配键改为「品牌 + 系列 + 容量」。
- 机箱补中文系列 → 英文型号别名表，否则维持演示价。

## 5. 采集数据与硬件主库的关联

### 5.1 唯一关联键

`hardware_id` 是唯一连接键，全链路不新建第二套 ID：

```
master(hardware_id) → catalog(hardware_id) → offer.hardware_id
```

`offer_id` 只是报价自身标识，允许同一 `hardware_id` 多条报价（`-01`、`-02` 后缀区分渠道）。

### 5.2 关联四步

1. **抽取**：把标题/SKU 文本交给 LLM，输出 `[品牌, 型号, 价格]`；无法拆分返回 `null`。
2. **归一化**：小写、去空格与营销词（`散片`、`盒装`、`店保`、`开票`、`顺丰`），统一 `RTX4070`/`RTX 4070`。
3. **主库查找**：按 `category + 品牌 + 型号` 精确匹配；同型号多品牌时用品牌消歧；同品牌多记录取规范条目。
4. **判定**：唯一命中 → 生成报价；0 命中或多命中 → 记为 `NO_LISTING` / 歧义，**不入库**。

### 5.3 映射状态机

| 状态 | 含义 | 是否入报价 |
| --- | --- | --- |
| `PENDING` | 尚未采集 | 否 |
| `LISTING_FOUND` | 找到商品但未定价 | 否 |
| `OBSERVED` | 已拆出型号与价格，通过规则校验 | 是 |
| `NO_LISTING` | 检索无对应商品 | 否 |
| `EXCLUDED_NOT_SELLABLE` | 不在可售池 | 否 |

## 6. 报价融合规则

1. **来源优先级**：`OWNER_VERIFIED` > `PLATFORM_OBSERVED` > `MOCK_DEMO`；同一硬件存在人工核验价时，观测价不写入。
2. **价格口径**：详情页/SKU 面板的到手价，单位整数分；`price_basis` 记录 `ITEM_DETAIL`、`SKU_PANEL` 或 `SEARCH_LIST`。
3. **新鲜度**：观测价必须带 `observed_at`；超过 14 天标记待复核，不参与「已核验」表述。
4. **多报价**：同一 `hardware_id` 保留多条时，求解取最低可用价，前端展示最低价 + 链接。
5. **禁止事项**：搜索卡片价不得直接当作单型号成交价；FAMILY 匹配不得定价；演示价不得计入覆盖率。

## 7. 质量门禁（代码层二次校验）

LLM 输出必须全部通过才允许写入 `offers.json`：

| 校验 | 规则 |
| --- | --- |
| 型号存在 | `brand + model` 在主库唯一命中 |
| 价格区间 | CPU 200–20,000 元；GPU 500–40,000 元；其他按类别区间；非正整数分拒绝 |
| 链接 | `https`，非 PCPartPicker，域名白名单 |
| 重复 | `offer_id` 唯一；同 `hardware_id` 合并策略见 §6 |
| 价格离散度 | 同型号样本 ≥2 时，价差 >50% 标记 `low_confidence`，仍可入库但需 `notes` |
| 抽取置信 | LLM 未返回结构化结果、或型号无法解析时丢弃，不猜 |

## 8. 上线发布

### 8.1 当前路径（已验证）

**报价当前不入库**，是 classpath 资源：

1. `python scripts/pc-config/ingest_offers.py --market data/.../market_offers.json` 生成 `application-service/src/main/resources/pc-config/offers.json`。
2. `catalog.json`、`benchmarks.json` 由 master 导出脚本生成，`catalog_version` 必须与 `offers.json` 一致。
3. 构建镜像时随 jar 打包；启动时 `JsonOfferRepository` 一次性加载并缓存。
4. 回滚 = 回滚镜像 tag；不涉及数据库迁移。

### 8.2 数据库方案【待实现】

需要「不重建镜像即可更新报价」时，再引入：

- `V25__create_pc_offer.sql`：`pc_offer` 表，主键 `offer_id`，`hardware_id` 外键语义（不建物理外键），字段与 `Offer` record 一一对应，额外加 `data_status`、`observed_at`、`imported_at`。
- 导入器：读 `offers.json` → 按 `offer_id` 幂等 upsert → 软删除本次未出现的观测价（不删人工核验）。
- 灰度：先写库、再切读路径，保留 JSON 兜底；契约（`Offer` 字段、错误码）不变。
- 校验：导入前后比对条数、类别分布、最低价差异；异常即中止并保留旧快照。

## 10. 当前快照与已知缺口

- 已发布：`catalog_version=2026-11-09-reference-9`，目录 1,519 条、报价 1,371 条（10 人工核验 / 18 演示 / 1,343 平台观测）、跑分 10 条，可售覆盖率 34.6%。
- 2026-11-10 引入档位中位价（见 §12.7）：机箱 +820、散热 +133、存储 +107、GPU +60、主板 +22；内存与电源因标题多规格混卖无法合法推导，仍未覆盖。

- **扩散风险**：主板/散热/电源存在「一条链接挂多个型号」，已按 EXACT-only 定价，仍需回溯收紧。
- 采集脚本已正式归档到 `scripts/pc-config/`：`harvest.py`、`match_market.py`、`enrich_market.py`、`bucket_pricing.py`、`merge_offers.py`、`derive_offers.py`、`ingest_offers.py`。

## 12. 采集计划 v2（2026-11-09）

### 12.1 在 3,967 可售池上再收缩

可售池类别分布：内存 1,107、机箱 822、散热 589、主板 512、电源 368、GPU 284、存储 214、CPU 71。

收缩不是砍类别，而是把「条数」换成「可定价单元」：

| 步骤 | 规则 | 剩余 |
| --- | --- | ---: |
| S0 | 可售池（品牌白名单 + 市场存在性） | 3,967 |
| S1 | 核心件只留近两代（CPU/GPU/主板/内存/存储）；机箱/散热/电源不按代际过滤 | 1,613 |
| S2 | 同芯片/同规格只留代表型号（GPU 按芯片、主板按芯片组×板型、内存按容量×频率、存储按型号） | 298 |
| S3 | 首轮只采 P0（CPU + GPU） | 95 |

S1 明细：内存 662、主板 391、GPU 275（26 个芯片）、存储 214、CPU 71；机箱/散热/电源只采兼容参数，不做逐件报价。

S2 明细：CPU 69、GPU 26、主板 22（芯片组×板型）、内存 55（容量×频率，DDR5）、存储 126（PCIe 4/5，1TB/2TB）。

### 12.2 排序：发布时间 + 硬件重要性

**发布时间**：主库没有 `release_date`，只能用代际序号近似「新旧」，同代内再按型号数字倒序（编号越大通常越新）。这是近似值，精确发布时间需要新增字段，当前未实现。

| 代际序 | CPU | GPU | 主板 | 内存 / 存储 |
| ---: | --- | --- | --- | --- |
| 5（最新） | Core Ultra 200、Ryzen 9000 | RTX 50、RX 9000 | B850/X870/X870E | DDR5、PCIe 5.0 |
| 4（上一代） | 13/14 代、Ryzen 7000/8000 | RTX 40、RX 7000、Arc B | B760/Z790/B650/X670 | DDR5、PCIe 4.0 |
| ≤3（更早） | 12 代及更早、Ryzen 5000 | RTX 30、RX 6000、Arc A | 600/500 系 | DDR4、PCIe 3.0 |

**重要性权重**：CPU 1.0、GPU 1.0、主板 0.8、内存 0.7、存储 0.7、电源 0.5、散热 0.4、机箱 0.3。理由是求解器评分主要由 CPU/GPU 决定，主板/内存决定兼容性，机箱/散热/电源只影响少量规则。

综合优先级 = 重要性 × 0.6 + 代际序/5 × 0.4，按分数降序采集：

1. P0：CPU/GPU 的 5 代与 4 代（95 个单元）。
2. P1：主板 22 组 → 内存 55 组 → 存储 126 组。
3. P2：电源按瓦数×品牌、散热按插槽×高度、机箱按板型×限高补充兼容参数，价格仅在需要时采。

### 12.3 分品类最高效通道

| 类别 | 主通道 | 检索串模板 | 说明 |
| --- | --- | --- | --- |
| CPU | A 搜索卡片 | `i5-14600KF 盒装`、`Ryzen 7 9800X3D 盒装` | 单型号标题占多数，EXACT 命中率高；散片/套装已由 `USED/BUNDLE` 过滤 |
| GPU | A 搜索卡片 + B SKU 面板 | `RTX 5060 Ti 16G`、`RX 9070 XT 16G` | 必须带显存；混卖链接走 SKU 面板，展示价不可直接定价 |
| 主板 | A 搜索卡片 | `微星 B850 TOMAHAWK`、`华硕 B860M` | 同一链接常挂多板型，要求芯片组 + 板型同时命中 |
| 内存 | A 搜索卡片 | `金士顿 DDR5 6000 32G 套装` | 按容量×频率聚合，不区分单条/套条价格 |
| 存储 | A 搜索卡片 | `致态 TiPlus7100 1TB`、`SN850X 2TB` | 按系列 + 容量匹配，避免不同容量串价 |
| 电源 | A 搜索卡片 | `海韵 FOCUS GX-850` | 瓦数 + 系列双条件 |
| 散热 | B 详情 | `利民 PA120 SE` | 重点是插槽、高度、风扇规格，价格次要 |
| 机箱 | B 详情 | `联力 216` | 重点是板型、限高、显卡长度，价格次要 |

所有通道共用同一套代码层门禁：价格在类别区间、`hardware_id` 在主库唯一命中、混卖/二手/拆机/海外直购直接剔除。

### 12.4 冷却与并发

- `chengkit-taobao` 的 `NORMAL_COOLDOWN_MS` 已从 20 秒调到 **10 秒**，`harvest.py` 的 `COOLDOWN` 同步为 10 秒。
- 单次搜索约 15–25 秒（打开、等待渲染、提取），叠加 10 秒冷却后实际吞吐约 **2–3 次/分钟**。
- **不支持多窗口并行**：MCP 侧固定使用 `site:taobao` 单一会话与前台窗口，冷却状态写在共享的 `state/taobao-browser-activity.json`，多个进程会互相抢冷却；`busy` 标记只在单进程内生效，强行并发会同时操作同一标签页，反而提高风控概率。
- 若确实要并行，只能开两个独立 OpenCLI session 错峰（一个跑 CPU、一个跑 GPU），但账号仍是同一个，项目不推荐，也不承诺收益。

### 12.6 风险

- 主库缺 `release_date`，代际排序只能近似；型号编号大小并非严格发布时间。
- 搜索展示价可能对应最便宜 SKU，多型号链接必须降级到详情/SKU。
- 同一淘宝账号高频搜索会触发登录/验证码；出现后停止，不自动重试。
- 白名单缺口（RX 9060 XT、RX 9070 XT、Silicon Power）未修复前，S1 计数会偏低。

### 12.7 档位中位价（T2，2026-11-10）

前提：报价只作中国区参考价，**不要求与真实商品一一对应**，因此允许用同档商品中位价为无法精确匹配的硬件补价。

- 档位定义（`scripts/pc-config/bucket_pricing.py`）：主板「芯片组 × 板型 × 内存类型」（样本不足时依次退化为「芯片组 × 板型」「芯片组」）、GPU「芯片 × 显存」、内存「代际 × 容量 × 频率」→「代际 × 容量」、存储「容量 × 接口」→「容量」、电源「瓦数档」、散热「风冷/水冷」、机箱「ATX/ITX」。CPU 不参与档位定价。
- 门禁：样本 ≥3、Tukey 围栏剔除极端值、价差分品类上限（GPU/主板/存储 0.6，内存 1.3，电源 2.0，散热 2.5，机箱 3.0）、中位价落在类别区间。
- 优先级：`SKU_PANEL > LISTING_MATCH > SEARCH_LIST > BUCKET`，档位价永不覆盖精确价；备注写「同档参考价、非单型号报价」，链接为档内代表商品。
- 已覆盖：机箱 825、散热 187、存储 117、GPU 75、主板 41。
- **无法突破**：内存与电源商品标题普遍写成「5200 5600 6000 6400 16G 32G」「650/750/850/1000W」，展示价对应最便宜规格，任何档位聚合都会失真，只能靠详情 SKU 面板拆解或单型号检索串补齐。
