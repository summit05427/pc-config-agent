# Stage 10：PC 配置求解器与硬件兼容性引擎专业化升级

## 一、任务目标

你是一名资深 Java 后端架构师、硬件兼容性工程师和算法工程师。

当前项目是一个基于 LLM 的 PC 配置智能推荐 Agent 应用。本阶段需要在现有四端架构和 Stage 1–9 的成果上，专业化升级 PC 配置求解器与硬件兼容性验证系统。

Stage 10 的核心目标：

1. 将现有基础硬件兼容性检查升级为更完整、可解释、可扩展的兼容性规则体系。
2. 引入用户使用场景，使求解器能够针对不同工作负载选择更合理的硬件组合。
3. 优化现有确定性 BuildSolver 的搜索、剪枝、评分和排序能力。
4. 确保预算、兼容性、性能和用户偏好之间有明确的决策规则。
5. 让每次配置推荐都能够解释为什么选择这些硬件，以及存在什么限制和风险。
6. 保证求解结果可复现，历史 BuildSnapshot 能还原当时的配置依据。

本阶段不是重建 PC 配置系统，而是在现有实现基础上进行有证据的改进。

**必须优先理解并复用当前代码。禁止为了实现所谓的专业化而重写已有的稳定模块。**

## 四、Stage 10.1：专业化硬件兼容性规则体系

这是 Stage 10 的核心工作之一。

目前基础兼容性不能仅依赖 CPU 插槽和内存类型判断。

需要逐步完善八大硬件之间的实际兼容关系。

### 4.1 CPU 与主板

检查：

- CPU Socket 与主板 Socket 是否一致；
- 主板芯片组是否支持目标 CPU；
- CPU 所需 BIOS 版本；
- 主板是否支持目标 CPU；
- BIOS 是否需要更新；
- 主板 VRM 能否满足 CPU 的实际供电需求；
- CPU 功耗与主板供电能力是否存在明显风险。

特别注意：

Socket 相同不代表 CPU 一定受到主板和 BIOS 支持。

不能仅根据 Socket 相同就判定 PASS。

没有可靠 BIOS 支持信息时，应返回 UNKNOWN 或相应的待核验状态，不得编造兼容性结论。

### 4.2 CPU 与散热器

检查：

- CPU 插槽支持；
- 散热器安装扣具支持；
- 散热器高度或冷排安装需求；
- CPU 散热需求与散热器能力是否匹配；
- 机箱是否能够容纳对应散热方案。

如果没有可靠的散热能力数据，不得直接根据散热器价格或品牌推断其压制能力。

### 4.3 内存与主板

检查：

- DDR 类型；
- 主板内存类型支持；
- 最大内存容量；
- DIMM 插槽数量；
- 单条内存容量支持；
- 内存频率支持；
- ECC / Registered 等特殊内存要求（有相关数据时）；
- 内存套装配置与插槽使用情况。

QVL 的处理原则：

- 官方 QVL 明确支持：可以作为已验证依据；
- 官方 QVL 明确不支持：需要结合实际兼容性规则判断，不能仅因未列出就判定绝对不兼容；
- 没有 QVL 数据：UNKNOWN，不能伪装为 PASS。

### 4.4 主板与机箱

检查：

- ATX、Micro-ATX、Mini-ITX 等板型；
- 机箱支持的主板尺寸；
- 主板和机箱安装限制；
- 扩展卡和安装空间限制（有可靠规格时）。

### 4.5 GPU 与机箱

检查：

- GPU 长度；
- GPU 厚度；
- GPU 插槽占用；
- 机箱最大显卡长度；
- 风扇或冷排安装对 GPU 空间的影响（数据具备时）。

不能只检查 GPU 长度而忽略厚度和其他结构干涉。

### 4.6 电源与整机

检查：

- CPU 功耗；
- GPU 功耗；
- 其余硬件功耗估算；
- 电源额定功率；
- 必要的功率余量；
- PCIe 供电接口；
- 12VHPWR / 12V-2x6 等接口（适用时）；
- 电源实际接口数量；
- GPU 和电源之间的供电需求。

必须区分：

- 额定功率；
- 估算整机负载；
- 峰值功耗；
- 供电接口兼容性。

不要只根据电源额定功率就判定整个供电系统完全兼容。

功率余量阈值必须来自明确的技术依据，并采用可配置或版本化规则。不能随意规定一个百分比后将其包装成行业标准。

### 4.7 存储与主板

检查：

- M.2 插槽数量；
- NVMe / SATA 接口支持；
- M.2 尺寸规格；
- PCIe 通道规格；
- M.2 与 SATA 接口之间的通道共享；
- 安装多个 SSD 时是否存在接口禁用或带宽限制。

如果主板存在通道共享，必须根据具体主板规格判断，不能仅根据拥有几个 M.2 插槽推断可以同时满速使用。

### 4.8 整机散热与物理空间

在现有规格支持范围内检查：

- CPU 散热器高度；
- 冷排尺寸及安装位置；
- GPU 空间；
- 电源长度；
- 主板安装空间；
- 散热方案之间的空间冲突。

没有可靠数据的项目返回 UNKNOWN，不允许通过默认值制造 PASS。

### 4.9 兼容性规则统一要求

所有规则应具有：

- 唯一规则 ID；
- 规则名称；
- 规则版本；
- 涉及的硬件类别；
- 所需输入字段；
- 判断条件；
- 结果状态；
- 失败原因；
- 用户可读解释；
- 数据来源或依据；
- 是否属于关键约束。

现有状态体系继续使用：

`PASS / WARNING / FAIL / UNKNOWN`

状态处理规则：

状态

Solver 行为

PASS

可以正常参与求解

WARNING

可以参与，但必须记录风险并影响排序或结果说明

FAIL

违反硬性兼容约束，不允许组成最终配置

UNKNOWN

信息不足，不能等同于 PASS

必须进一步设计 UNKNOWN 的策略：

- 对于 Socket、内存类型、物理空间、关键供电接口等硬性约束，如果必要数据缺失，应阻止系统将配置标记为完全验证通过。
- 对于非关键或暂时无法获取的辅助信息，可以允许配置继续求解，但必须显示待核验事项。
- 不能将所有 UNKNOWN 一律判定为 FAIL，否则可能因为现有数据不完整而无法生成任何配置。
- 也不能将所有 UNKNOWN 自动当作 PASS。

建议形成规则级别的风险策略，例如 `BLOCKING`、`ADVISORY`，但先检查现有设计，避免重复引入字段。

所有规则都必须可测试、可解释、可版本化。

## 五、Stage 10.2：引入不同用户工作负载与配置用途

目前用户的 PC 配置需求不能仅通过预算和硬件偏好表达。

应增加用途识别，让求解器根据不同工作负载选择更合理的硬件。

首期支持以下用途：

Workload Profile

主要优化方向

`GENERAL`

综合均衡、日常使用

`GAMING`

游戏性能，CPU/GPU 配比

`VIDEO_EDITING`

视频编辑、CPU/GPU、内存和存储

`PROGRAMMING`

CPU 多核能力、内存容量、SSD

`RENDERING`

CPU 或 GPU 渲染能力

`AI_INFERENCE`

本地推理所需的 GPU 显存和计算能力，以及系统内存

### 5.1 用途识别

在用户输入阶段尽可能提取：

- 主要用途；
- 是否涉及多个用途；
- 预算；
- 对性能的优先级；
- 是否偏重性价比；
- 游戏分辨率和目标刷新率（用户提供时）；
- 需要处理的视频分辨率、工作流（用户提供时）；
- 开发场景和运行工具；
- 渲染主要依赖 CPU 还是 GPU；
- AI 推理是否本地运行；
- 内存、显存和存储容量偏好。

不要强制要求用户填写大量参数。

只有当缺少的信息会明显改变配置结果时，才考虑通过现有澄清机制询问。

### 5.2 用途评分规则

需要设计可配置、可版本化的工作负载评分策略。

示例：

**GENERAL**

追求各类硬件之间的均衡，不对 GPU 或 CPU 赋予过度偏重。

**GAMING**

主要考虑：

- GPU 性能；
- CPU 游戏相关性能；
- 显存容量；
- CPU/GPU 性能搭配；
- 目标分辨率和刷新率（信息具备时）。

不能把 PassMark 综合分数直接等同于实际游戏 FPS。

**VIDEO\_EDITING**

主要考虑：

- CPU 性能；
- GPU 加速能力；
- 内存容量；
- SSD 容量与性能；
- 视频分辨率、编码格式和软件工作流（具备数据时）。

不同软件的硬件加速路径可能不同，不能声称所有视频编辑软件都会按照同一个硬件权重运行。

**PROGRAMMING**

主要考虑：

- CPU 多核性能；
- 内存容量；
- SSD；
- 是否存在大型项目编译、虚拟机、容器等需求。

**RENDERING**

应区分 CPU 渲染和 GPU 渲染。

如果用户需求没有说明，且该信息会改变配置方向，应使用已有澄清流程。

**AI\_INFERENCE**

主要考虑：

- GPU 显存；
- GPU 计算能力；
- 系统内存；
- 存储容量；
- 实际推理模型的硬件需求（具备数据时）。

不要仅根据显存大小承诺模型一定能运行，也不要捏造 Token/s、推理速度等没有实际 Benchmark 支持的数据。

### 5.3 评分权威与配置边界

工作负载识别可以由 Agent 的 `requirement_parser` 提取，但：

- Agent 只负责输出结构化需求；
- Java 负责最终评分；
- 权重和规则由 Java 业务端管理；
- LLM 不直接计算最终硬件分数；
- 不能将用途标签直接映射成未经验证的固定配置。

检查当前请求 DTO 和 Agent/Java 契约，按最小必要字段扩展。

建议使用明确的 `workload_profile`，必要时保留用户原始偏好和补充参数。

用途评分规则应有独立版本，便于回放历史配置。

## 六、Stage 10.3：BuildSolver 搜索和评分算法升级

当前项目已经有确定性 BuildSolver。

本阶段目标是增强现有实现，而不是默认替换算法。

### 6.1 硬性条件与软性目标分离

求解流程必须明确分为两部分。

**硬性条件：**

- 必须满足用户预算；
- 必须满足八大硬件类别的完整性要求；
- 必须满足关键硬件兼容性约束；
- 不允许使用无效报价；
- 不允许使用 MOCK；
- 不允许违反明确的用户硬件要求；
- 不允许将 FAIL 兼容性组合放入最终配置。

**软性目标：**

- 工作负载性能；
- 性价比；
- 性能均衡；
- 用户指定偏好；
- 兼容性 WARNING 数量及严重程度；
- 硬件升级空间（具备可靠数据时）。

软性评分不能覆盖硬性条件。

即使某个 GPU 性能很高，只要整机超出预算或存在明确硬件冲突，也不能通过高分进入最终结果。

### 6.2 搜索与剪枝

分析现有 Cartesian Product 或其他组合生成方式是否存在性能问题。

优先采用已有确定性算法进行增强，例如：

- 候选预过滤；
- 硬约束提前淘汰；
- 按价格和性能排序；
- 预算剪枝；
- 兼容性提前判断；
- 分支限界；
- 缓存重复的兼容性检查；
- 避免重复计算评分。

需要明确：

- 哪些规则可以在组合之前判断；
- 哪些规则必须在组合过程中判断；
- 哪些约束只能在完整配置形成后判断。

优化过程中不能因为剪枝而丢失合法解。

### 6.3 评分与排序

建立清晰的综合评分体系。

建议分解为：

- `performance_score`
- `value_score`
- `balance_score`
- `compatibility_score`
- `preference_score`

实际是否需要所有分项，以当前算法和测试结果决定。

评分必须：

1. 有明确的计算逻辑；
2. 不同用途采用不同配置策略；
3. 评分参数能够版本化；
4. 能解释各项得分来源；
5. 对缺失 Benchmark 有明确处理方式；
6. 不使用伪造 Benchmark；
7. 不使用未经核验的价格；
8. 同样输入得到确定性结果。

不同硬件类别的性能分数不能简单相加后直接比较，必须考虑各类别内的归一化方式和工作负载适配方式。

如果某种用途缺少对应的真实 Benchmark，应明确降低结论可信度，使用现有可用指标，并展示限制。

### 6.4 预算优化

预算始终是硬性限制。

必须保证：

`total_price_fen <= budget_fen`

所有价格运算使用整数分，不使用浮点数。

在满足预算和兼容性条件后，才对性能、均衡和性价比进行排序。

价格更新、报价缺失或报价过期时，不能继续使用旧值伪装成当前有效报价。

### 6.5 OR-Tools 的使用决策

不要因为 OR-Tools 能做约束优化，就默认引入它。

先评估当前确定性搜索算法。

只有满足以下条件，才可以提出 OR-Tools 引入方案：

- 当前算法在实际候选规模下存在可复现的性能问题；
- 已尝试合理的预过滤、剪枝和缓存优化；
- 仍然无法满足项目规定的求解时间或搜索规模目标；
- 能通过测试证明 OR-Tools 可以解决现有问题；
- 评估依赖成本、部署体积、可维护性和结果确定性。

如果没有充分证据，继续使用现有 Java 确定性求解器。

不能为了使用新技术而增加依赖。

## 七、Stage 10.4：求解结果解释和 BuildSnapshot 完善

用户不应该只看到八个硬件型号和一个总价。

求解结果应能够解释：

### 配置选择

- 为什么选中当前 CPU；
- 为什么选择这张 GPU；
- 为什么使用当前主板；
- 哪些硬件对性能贡献最大；
- 预算如何分配；
- 当前方案是否偏重某个硬件；
- 是否存在值得注意的兼容性 WARNING。

### 用途适配

明确说明配置针对什么工作负载进行了优化。

例如：

- 游戏性能优先；
- 视频编辑优先；
- 编译与开发优先；
- CPU 渲染；
- GPU 渲染；
- 本地 AI 推理。

不能声称配置对所有用途都达到最优。

### 兼容性说明

展示：

- PASS；
- WARNING；
- 尚未确认的 UNKNOWN；
- 已被排除的冲突组合及原因（适合时）。

不能将 UNKNOWN 显示成 PASS。

### 性能数据

展示真实 Benchmark 来源和指标。

如果使用的是 PassMark 数据，应明确标识是 PassMark 指标，不要直接将其解释成实际游戏帧率、渲染时间或 AI 推理速度。

### BuildSnapshot

检查现有快照能否保存：

- 选中的八类硬件；
- 商品与 Offer 快照；
- 当时价格；
- 当时预算；
- 兼容性结果；
- 规则版本；
- Workload Profile；
- Solver 版本；
- 评分策略版本；
- 评分结果；
- 必要的解释信息。

历史 BuildSnapshot 必须不可变。

规则升级和价格变化不能改变已经生成的历史配置。

如果目前快照缺少必要字段，再评估是否需要数据库迁移。不得为了保存所有中间计算数据而无意义地扩大 Snapshot。

## 九、Stage 10 测试与验收

测试必须覆盖真实业务规则，不允许只写空壳测试。

### 9.1 兼容性测试

至少覆盖：

1. CPU Socket 不匹配；
2. CPU 与主板芯片组不支持；
3. BIOS 版本不满足要求；
4. 内存 DDR 类型不匹配；
5. 内存容量超过主板限制；
6. 主板尺寸超过机箱支持范围；
7. GPU 长度超过机箱限制；
8. 散热器高度不满足机箱要求；
9. 电源功率不足；
10. 电源接口不满足 GPU 供电需求；
11. M.2 与 SATA 通道冲突；
12. 必要规格缺失导致 UNKNOWN；
13. WARNING 不被错误当作 FAIL；
14. FAIL 组合不能进入最终配置。

上述规则如果当前真实数据缺失，应使用明确标注为测试用途的 fixture 验证规则逻辑，不能伪造生产硬件数据。

### 9.2 工作负载测试

至少覆盖：

场景

核心验证

GENERAL

均衡配置

GAMING

GPU 和 CPU 游戏性能匹配

VIDEO\_EDITING

CPU、GPU、内存及存储策略

PROGRAMMING

CPU 多核和内存需求

RENDERING

CPU/GPU 渲染方向

AI\_INFERENCE

显存和推理相关约束

验证同一组硬件在不同工作负载下，求解排序是否符合策略。

不要为了让测试通过而硬编码不同用途选出不同硬件。结果必须由评分策略和实际数据决定。

### 9.3 Solver 测试

至少覆盖：

- 预算内存在合法解；
- 预算内不存在合法解；
- 报价过期；
- 无有效报价；
- 商品类别缺失；
- 兼容性 FAIL；
- 兼容性 WARNING；
- UNKNOWN；
- 多个合法组合；
- 多平台 Offer；
- 多个商家报价；
- 重复候选；
- 大候选池；
- 相同输入的确定性；
- 价格更新后历史快照不变。

### 9.4 性能测试

使用受控、可重复的数据集模拟不同候选规模。

记录：

- 候选数量；
- 组合搜索规模；
- 剪枝数量；
- 求解耗时；
- 最终解数量；
- 评分耗时；
- 兼容性规则调用次数。

不要只报告优化后的耗时，必须提供优化前后可对比的基准。

不得虚构性能提升百分比。

### 9.5 完整 E2E

使用当前可用的合法报价数据完成真实链路测试。

如果 Stage 9 采集尚未覆盖全部八类：

- 不允许使用 MOCK 证明生产完整链路通过；
- 可以使用隔离测试 fixture 验证算法；
- 必须明确真实数据 E2E 尚未完成；
- 不得将算法测试通过写成真实市场配置已经通过。

## 十、Stage 10 与 Stage 9 的并行协作要求

目前 Stage 9 的商品采集正在进行。

Stage 10 可以与 Stage 9 并行推进，但必须注意：

1. 不修改正在更新的 `offers.json`，除非确实属于 Stage 10 必要的代码契约变更，并且先保护当前数据。
2. 不清理 Stage 9 已生成的映射请求、商品采集结果和数据报告。
3. 不擅自调整 Stage 9 已确定的 P0/P1/P2 口径。
4. 不为了求解器测试把 MOCK 数据加入生产报价。
5. 兼容性规则应尽量依赖标准硬件规格，不应依赖淘宝或京东特有字段。
6. 如果某项规则需要的规格当前不存在，记录数据缺口，并设计 UNKNOWN 处理。
7. Stage 10 的代码测试可以使用独立的受控测试 fixture，不应修改 Stage 9 正在积累的真实商品数据。
8. 后续真实数据 E2E 可以在 Stage 9 完成首批 Offer 导入后补齐。

Stage 9 与 Stage 10 共享数据契约，但不能让它们互相覆盖未完成的工作。
