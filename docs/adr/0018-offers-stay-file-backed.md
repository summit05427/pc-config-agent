# 报价继续以文件产物承载，不建 Offer / Mapping / Import Batch 表

## 背景

当前 `Offer` 没有任何数据库表：报价唯一来源是 `application-service/src/main/resources/pc-config/offers.json`，由 `JsonOfferRepository` 在启动时读取；Flyway 最新为 `V24`，只有 `pc_build_snapshots`，报价以 `offer_snapshot jsonb` 写入快照。

Stage 9 要接入真实商品报价，原方案规划了三张表（商品映射、报价、导入批次）与批次状态机。但首期规模只有八类各 1 款、共 8 条报价，且采集是低频人工触发。

## 决策

1. 报价继续以整份 `offers.json` 承载，发布方式为「内存校验通过后整份重写」，不新建 Offer、Product Mapping、Import Batch 表。
2. 不新增 Flyway 迁移；报价沿用硬件主数据 `catalog_version`，同版本内允许多次发布，用 `observed_at` 与发布清单批次区分。
3. 商品映射是离线产物（映射请求清单与采集结果），不是运行时实体。
4. 数据库化留待报价规模达到数千条或需要并发写入时再评估。

## 考虑过的替代方案

- **建三张表 + 批次状态机**：为 8 条数据准备几千条数据的基础设施，导入事务、状态迁移与回滚都要维护，违反「不新增无消费者能力」。
- **只建报价表，不建映射表**：仍要处理迁移、连接池与测试夹具，收益不足以抵消复杂度。
- **报价写入 Redis**：不适合作业可追溯的权威数据源，且与现有 classpath 加载方式冲突。

## 影响

- 刷新必须整文件重发，未出现在新结果中的报价会被移除；因此发布前必须做差集核对，避免误删仍有效的报价。
- 回滚成本极低：保留上一版 `offers.json` 即可恢复。
- `Offer` 只允许新增可空字段，保证旧文件仍可加载。
- 一旦报价规模扩大，本决策需要重开，并补一次「文件 → 数据库」的迁移设计。
