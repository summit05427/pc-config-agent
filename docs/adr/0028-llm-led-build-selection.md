# PC 配置选型决策权迁移到 LLM，Java 保留事实与验证权威

过渡期方案：本决策推翻 [PC 配置术语](../pc-config/glossary.md) 中「求解器不允许 LLM 选择最终 SKU」的表述。当年引入的 `AGENT__PC_SELECTION_MODE` 用于在 `llm` 与 `solver` 两条路径间切换；该配置项与求解器路径已于 2026-11-17 一并移除，仅保留 `BuildSolver` 作为离线基线对照臂。

## 背景

现状（见 [交接说明](../pc-config/current-task-flow-handoff.md)）是 LLM 只解析需求与撰写说明，`BuildSolver` 决定最终组合。方案要求 LLM 看到真实候选并输出所选 `hardware_id`，这实际上改变了「谁拥有选型权」这一领域不变量，需要单独记录，避免后续实现者按旧语义"纠正"回来。

## 决策

1. **选型决策权归 LLM**：Build Architect 只能从 Java 本轮召回集（候选召回集）中选择 `hardware_id`，并输出结构化方案提案。
2. **事实权威归 Java**：型号、规格、跑分、报价、链接、预算与兼容性结论只能来自 Java 的校验报告；Agent 不得生成，也不得把提案里的复制字段当作展示源。
3. **求解器降级为基线**：`BuildSolver` 保留为离线对照、回归样本来源与产品开关控制的显式降级路径；禁止静默覆盖 LLM 的选型结果。
4. **硬约束不由模型放宽**：预算上限、物理兼容、报价政策与用户强制条件只由代码判定。

## 未采用的替代方案

- **只改进求解器**（多通道召回、偏好权重、候选池去重、性能优化）：成本更低，但不满足「LLM 主导决策」的产品定位。保留为对照臂，不作为替代。
- **LLM 自由选型**（不受召回集约束）：无法评测召回覆盖率，也无法阻止编造型号，故不采用。

## 后果

- 新增「部分兼容性校验」能力：现有 `validate` 强制八类齐全，无法支撑逐步组装。
- `方案提案（Build Proposal，未验证）` 与 `配置方案（PC Build，已通过 Java 校验）` 成为两个必须区分的领域实体。
- 每次推荐必须记录决策模式（`LLM_LED` / `DETERMINISTIC_FALLBACK`），不得混淆。
- 选型失败时不允许回退到求解器并冒充 LLM 结果。

## 门禁（未满足则回退本决策）

- LLM 的选择域严格等于本轮召回集，越界即判定该轮失败。
- 对照评测：12 个评测场景上硬约束通过率 100%，总质量分不低于基线求解器，单场景不得低于基线 10 分以上；p95 ≤ 120 秒；单轮 LLM 调用 ≤ 5 次；单次成本 ≤ ¥0.3。
- 任何兼容性 `UNKNOWN` 被表述为 `PASS`，视为失败。
- 判据细则见 [重构方案 §22.4](../planning/pc-config-agent-refactor-plan-v1.md)。
