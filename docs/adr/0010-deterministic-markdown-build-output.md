# 配置结果由后端确定性渲染，并通过 done 事件附带结构化结果

| 项 | 内容 |
| --- | --- |
| 状态 | Accepted |
| 决策日期 | 2026-11-08 |
| 修订 | 取代同日早先“仅 Markdown、`done` 不带结构化结果”的草稿 |
| 相关 | ADR-0009、`docs/planning/pc-config-implementation-plan.md` §7.5 |

## 背景

PC 配置结果必须包含八件硬件的型号、参数、单价、购买链接、跑分、总价、预算状态、兼容性状态、报价核验时间与推荐说明。现有 SSE 只有 `token` / `reasoning` / `tool_call` / `tool_result` / `citations` / `done` / `error` 七类事件，没有承载结构化业务结果的事件。

同时有两条硬约束：

1. LLM 不得重组型号、价格、链接、SKU 与总价；
2. 展示必须完整，不能因为窄屏把表格压到不可读。

## 决策

1. Java 返回结构化 `BuildResult`，它是配置结果的唯一事实来源。
2. Agent 的 `response_generator` 用**代码模板**把结构化字段渲染为 Markdown，经现有 `token` 事件输出，作为兜底与导出形式。
3. `done` 事件在保留 `thread_id` 的同时，追加**可选** `build_result` 字段（前端消费子集见计划 §7.5）。旧客户端忽略该字段即可，不构成破坏性变更。
4. 前端新增 `BuildResultCard` 读取 `build_result` 渲染卡片；字段缺失时回退到 `MarkdownContent`，保证历史会话可回放。
5. LLM 只生成推荐摘要、选型理由、预算分配解释与兼容性提示，不接触型号、价格、链接、SKU、总价这些字段。

## 考虑过的替代方案

- **仅 Markdown，不改 `done`**：契约零变更，但 8 类 × 多字段的宽表在聊天窄屏下不可读，且未来“对比/替换”缺少结构化入口。
- **新增 `build_result` SSE 事件**：语义最清晰，但需要同时改 Agent、前端类型、契约文档与事件快照测试，收益与 `done` 追加字段相同。
- **启用 OpenUI 渲染卡片**：默认关闭，需要前后端同步开启并生成组件提示词产物，模型输出稳定性不可控，不作为本期前置。
- **前端从 Markdown 反解析结构化数据**：脆弱的双向耦合，禁止。

## 影响

- SSE 事件类型不变；`done` 的 payload 向后兼容地增加一个可选字段。
- 前端需要新增类型与卡片组件，并保证无 `build_result` 的旧会话正常回放。
- 渲染逻辑必须在 Agent 侧且可单测；不得把字段拼接交给 LLM。
- 契约文档、前端类型、Agent 类型与事件快照测试必须同步更新，避免只改一端。
- 若未来确需独立事件，可在保持 `done.build_result` 的前提下再新增事件，不需要推翻本次实现。
