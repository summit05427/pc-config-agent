# 保留 MCP 客户端，不对外暴露 MCP Server

## 背景

Stage 11 任务书 §8 把 MCP 描述为「尚未引入、需要评估是否引入」。审计发现该前提不成立：仓库已实现经 LiteLLM 网关的 MCP **客户端**（`agent-service/app/agent/mcp.py`），`mcp` 与 `langchain-mcp-adapters` 已是直接依赖，工具按 `mcp__<tool>` 命名进入同一套 ToolSpec 治理链，默认关闭（`MCP__ENABLED`）。

因此真正待决的不是「要不要用 MCP」，而是三件事：存量客户端是否保留、是否把本项目对外暴露为 MCP Server、是否让 Java 内部 API 改走 MCP。

## 决策

1. **保留**现有 MCP 客户端与网关拓扑（Server 清单由 LiteLLM 托管，Agent 只连 `{网关}/mcp`），默认关闭，由部署方按需开启。
2. **不**把本项目对外暴露为 MCP Server。当前没有第二个 AI 客户端消费本项目工具的需求，对外暴露会新增鉴权面、审计面与工具越权风险，收益为零。
3. **不**让 Java 内部 API 改走 MCP。`/internal/v1/**` 服务令牌 + `X-User-Token` 的职责分离是既有安全基线，换协议不改变契约语义，只会增加运维与排障成本。
4. 重新评估条件：出现第二个独立 AI 客户端需要复用本项目的 PC 配置工具，或外部硬件数据服务只提供 MCP 接口且无 HTTP 等价物。

## 考虑过的替代方案

- **移除 MCP 客户端与依赖**：可以缩小供应链面，但会丢弃已通过治理链与测试的接入能力，且重新引入时需要重做工具命名、冲突检测与网关鉴权，成本高于保留。
- **对外暴露 MCP Server**：技术上可行，但当前没有消费方；在无需求时开放协议入口违反「不为技术而技术」的既定边界。
- **Java 全面 MCP 化**：把内部 HTTP 契约替换为 MCP 工具调用，会让服务间鉴权、幂等与错误码体系失去统一入口，属于不可接受的架构倒退。

## 影响

- Stage 11.5 的交付物是「存量 MCP 收口说明」，不是新实现；不得为了「完整」而安装新的 MCP 依赖或增加 Server 方向代码。
- MCP 工具继续受 ToolSpec 的超时、重试、角色、单轮上限与输出脱敏约束；不允许另建权限体系。
- `docs/services/agent-service/architecture.md` 中「无 MCP 工具接入」的表述已过期，需在后续文档修订中纠正。
