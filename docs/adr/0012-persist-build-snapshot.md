# 配置结果落库为不可变快照

| 项 | 内容 |
| --- | --- |
| 状态 | Accepted |
| 决策日期 | 2026-11-08 |
| 相关 | ADR-0010、`docs/planning/pc-config-implementation-plan.md` §7.4 |

## 背景

本期目标是让 PC 配置推荐可演示。上一版计划选择“配置结果只在内存返回，`build_id` 仅进程内有效”，理由是减少改动。

但产品明确要求后续扩展**多方案对比、瓶颈分析、交互式硬件替换**。这三项都依赖“配置结果在创建时刻的不可变副本”：商品报价会变、跑分会更新、候选集会调整；如果每次回看都重新求解，历史结果会漂移，“当时为什么推荐这套”无法回答。

## 决策

1. 新增 append-only 表 `pc_build_snapshots`（Flyway `V24`），保存 `build_id`、`user_id`、`thread_id`、结构化 `build_json`、总价与预算字段、`solver_version`、`compatibility_rule_version`、`catalog_version`、`created_at`。
2. 快照由 Java 在 `POST /internal/v1/pc/builds/solve` 成功返回前写入；求解与落库在同一业务事务内，避免“返回了但没存”。
3. 提供 `GET /internal/v1/pc/builds/{buildId}`，按 `X-User-Token` 校验归属；不属于当前用户的快照一律视为不存在。
4. 前端本期不展示历史快照列表，只使用 `done.build_result` 中的当次结果；查询接口用于未来扩展与联调验证。
5. 快照不可更新、不可覆盖；同一 `build_id` 重复写入必须失败或幂等忽略，禁止静默改写。

## 考虑过的替代方案

- **不落库**：改动最小，但未来对比与替换需要重建整套持久化，且历史结果不可复现。
- **只存 `build_id` 与输入需求，回看时重新求解**：节省存储，但报价与跑分变化会导致结果漂移，无法解释当时的推荐。
- **完整版本化数据模型（硬件、报价、跑分都做版本表）**：最严谨，但超出本期范围，且与“手工报价数据集”策略冲突。

## 影响

- 新增一张表与一个只读接口；不改硬件、报价、跑分的存储方式。
- 快照包含用户标识，必须遵守归属校验与最小化原则：不写入请求头、令牌或完整对话内容。
- 存储随使用增长；本期只增不删，保留期限列为待确认事项（计划 §10 O3）。
- 未来切换硬件数据到 PostgreSQL 或引入自动报价时，快照结构不需要改变。
