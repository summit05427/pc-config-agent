# 复杂场景放宽单轮 LLM 调用上限到 9 次

## 背景

现有门禁要求「单轮 LLM 调用 ≤ 5 次」，它诞生于单 Agent 架构：需求解析、策略、Architect、修正与质量评审共用 5 次预算。Stage 4 的多 Agent 方案会增加 Strategist 调度、多个并行 Specialist 与 Critic；即使只启用两个 Specialist，单轮调用也会达到 6–7 次。若继续沿用 5 次，只能通过停用 Specialist 通过门禁，等于让门禁否定多 Agent 本身。

这是一个产品取舍，不是实现细节：放宽调用次数会带来延迟与成本上升，需要单独记录，避免后续实现者以为可以随意超额。

## 决策

1. **简单任务保持 ≤ 5 次**：未启用 Specialist 的路径（Stage 1/2/3 能力）继续受 5 次上限约束，不得因为引入多 Agent 而整体放宽。
2. **复杂任务放宽到 ≤ 9 次**：仅当本轮显式启用了 Specialist 或 Critic 时生效；判定依据是图状态里的启用标记，不是模型自由文本。9 次来自最坏路径：需求解析 1 + Strategist 1 + Specialist 2 + Architect 首提案 1 + Critic 1 + Critic 修正（重提案 1 + 内部修正 1）+ 收尾 1。
3. **Critic 修正只允许一次**：仅 `REVISE` 且存在 `HIGH`/`MEDIUM` 问题时回 Architect；Architect 入口把已用修正配额抬到上限前一位，重提案后最多再修一次，标记消费后清空，不可能二次进入。
4. **超预算即失败**：单轮调用数超过对应上限时，该轮按失败处理并记录 `run_budget_exceeded`，不得截断统计或事后补算。
5. **收益必须用评测证明**：多 Agent 的验收对照单 Agent 基线，除质量指标外必须同时汇报单轮最大调用、p95 时延与单次成本；成本收益不成立时回退本决策。

## 未采用的替代方案

- **维持 5 次上限**：会迫使 Specialist 在复杂场景串联执行或直接停用，失去并行收益，也无法验证 Critic 的价值。
- **取消调用上限**：失去成本护栏，复杂场景可能反复调用工具与模型，单次成本不可控。
- **按 token 而非调用次数限制**：token 与实际请求次数、工具往返次数不呈线性关系，无法约束「反复试错」。

## 后果

- 评测报告需要区分「简单路径」与「复杂路径」两套调用预算，单例结果必须记录是否启用 Specialist。
- `EVALS` 报告继续输出 `max_turn_llm_calls`；多 Agent 验收用例按场景声明自己的上限（当前 9）。
- 延迟门禁 p95 ≤ 120 秒保持不变；调用次数放宽不等于可以牺牲时延。
- 若实测复杂场景稳定低于 9 次，应下调上限，而不是保留余量。
